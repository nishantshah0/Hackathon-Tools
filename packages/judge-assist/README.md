# judge-assist

AI system to shorten hackathon judging time.

Judging is the slowest part of a hackathon: every judge spends ~10 minutes just
figuring out what each project *is*, then agonizes over rubric numbers on a
personal scale nobody else shares, and no judge can see every project anyway.
`judge-assist` attacks all of that:

1. **AI judge briefs** — one-page orientation sheets per submission (summary,
   tech stack, what to click/run, questions to ask, risk flags) so judges spend
   their minutes evaluating instead of orienting.
2. **Pairwise A/B scheduling** — instead of slow rubric scoring, each judge makes
   fast binary "A or B?" calls. The scheduler balances coverage, respects
   conflicts of interest, and (in adaptive rounds) targets the most informative
   matchups.
3. **Bradley-Terry ranking** — turns those sparse pairwise votes into a fair
   global ranking with confidence measures and judge-agreement stats, even
   though no judge saw every project.
4. **Score normalization** — for events that also collect raw rubric scores,
   per-judge z-scoring removes harsh-judge/generous-judge luck from the results.

Everything works **fully offline** — no API key required for the demo, the
tests, the scheduler, the ranking, or the normalizer. An `ANTHROPIC_API_KEY`
upgrades briefs from deterministic heuristics to AI-written one-pagers.

## Quickstart

```sh
npm install
npm test          # 38 tests, all offline
npm run demo      # end-to-end simulation: schedule → vote → rank → compare vs truth

# Generate judge briefs (AI if ANTHROPIC_API_KEY is set, heuristic otherwise)
node bin/cli.js brief examples/submissions.json --out briefs.json

# Schedule 8 pairwise comparisons per judge
node bin/cli.js schedule examples/submissions.json \
  --judges examples/judges.json --per-judge 8 --seed 1 --out assignments.json

# Rank from collected pairwise results
node bin/cli.js rank examples/results.json

# Normalize raw rubric scores (optionally weighting criteria)
node bin/cli.js normalize examples/scores.json --weights '{"technical":2,"design":1}'
```

## The three components (plus one)

### 1. AI judge briefs (`src/brief.js`)

Input: a submission `{id, team, title, description, repoUrl, videoTranscript?,
readme?, techStack?}`. Output: a brief matching `BRIEF_SCHEMA`:

- `summary` — two plain-language sentences
- `techStack` — what's actually used
- `noveltyNotes` — what's new vs off-the-shelf
- `whatToTry` — concrete "click this / run this" steps
- `suggestedQuestions` — 3 sharp questions for the team
- `riskFlags` — e.g. "demo video doesn't show the feature described"
- `rubricHints` — one-sentence *observations* per rubric axis
  (`technicalDepth` / `completeness` / `originality`). Never scores — judges
  score, the AI orients.

The AI path uses the Anthropic Messages API with **structured output**
(`output_config.format` with a JSON schema), so responses are guaranteed valid
JSON matching the schema. Model: `claude-opus-4-8` by default, override with
`ANTHROPIC_MODEL`. Batch generation caps concurrency at 3.

**Offline fallback:** with no API key (or on any API failure) briefs are
generated by a deterministic heuristic (keyword-table tech-stack extraction,
first-sentence summaries, generic try-this steps) and marked
`"source": "heuristic"` vs `"source": "ai"`.

**Caching:** AI briefs are cached in `.briefs-cache.json`, keyed by a content
hash of the submission + model, so re-runs never re-pay for unchanged
submissions.

### 2. Pairwise comparison scheduler (`src/schedule.js`)

`scheduleComparisons({submissions, judges, perJudge, seed, strengths?})`
greedily picks, for each judge slot, the pair minimizing a cost that combines:

- overall appearance balance (projects seen least come first),
- per-judge repetition (a judge shouldn't see the same project over and over),
- conflict-of-interest exclusions (`judge.excludedTeams` — hard constraint),
- and, when `strengths` from a previous Bradley-Terry round are supplied, the
  strength gap between the pair — close matchups carry the most information,
  so adaptive rounds sharpen exactly where the ranking is still uncertain.

Deterministic for a given `--seed` (mulberry32 PRNG, used only for tie-breaks).

### 3. Bradley-Terry ranking (`src/rank.js`) — how the math works

The Bradley-Terry model assumes each project has a latent strength `p_i > 0`
and that judge votes follow

```
P(i beats j) = p_i / (p_i + p_j)
```

Given sparse vote data, we find the maximum-likelihood strengths with the
classic iterative **MM / Zermelo** update:

```
p_i ← W_i / Σ_j  n_ij / (p_i + p_j)
```

where `W_i` is i's win count and `n_ij` the games between i and j, iterated to
a convergence tolerance on log-strengths. Because a raw MLE sends an undefeated
project to +∞ (and a winless one to 0), each project also gets `ε = 0.5`
virtual wins **and** losses against a dummy opponent of fixed strength 1 —
a light prior that keeps everything finite without distorting well-sampled
projects.

Output: normalized strengths, a ranking with scores, a per-project
**confidence** (more comparisons + a wider strength gap to neighbors = more
confident), and **judge-agreement stats** — how often each judge's votes agree
with the final ranking, with outlier judges flagged.

Why this beats "average of rubric scores": strengths are inferred jointly from
who-beat-whom, so it doesn't matter that different judges saw different
subsets, and one weird judge can't skew a project they happened to draw.

### 4. Score normalization (`src/normalize.js`)

For events that also collect raw rubric scores. **Raw averages are unfair**:
judges see different subsets and use different personal scales — one judge's
6/10 is another's 9/10, so a project's raw average mostly measures *which
judges it drew*, not how good it is.

Per-judge z-scoring fixes this: for each judge we compute the mean and standard
deviation of the scores *they* gave, and re-express every score as

```
z = (score − judgeMean) / judgeStd
```

i.e. "how far above this judge's own average was this project." A project's
normalized score is the mean z across its judges, so a harsh judge's 6 and a
generous judge's 9 can land in exactly the same place. Details:

- **Criteria:** scores with a `criterion` are normalized per (judge, criterion)
  — a judge can be harsh on `technical` but generous on `design` — then
  combined per project with equal weights or `--weights '{"technical":2}'`.
- **stddev = 0** (judge gave everything the same number): z = 0 — that judge
  expressed no preference and contributes no signal.
- **Small samples:** a judge with fewer than 3 scores has unreliable personal
  stats, so their mean/std are shrunk toward the global mean/std with weight
  `λ = n/3` (`stats' = λ·own + (1−λ)·global`).

The CLI report shows judge calibration (leniency ranking) and each project's
raw rank vs normalized rank with movement markers (`▲2` / `▼1`) — watch
projects that drew generous judges sink and harsh-judge victims rise.

## End-to-end demo (`npm run demo`)

`simulate` proves the whole pipeline: it assigns hidden true qualities to the
12 sample projects, schedules two rounds of comparisons (the second round is
adaptive, fed round-one Bradley-Terry strengths), simulates noisy judge votes
from the hidden truth, fits Bradley-Terry, and reports the recovered ranking
next to the true one with **Kendall tau**. With 5 judges × 8 comparisons (40
votes — 12% of the 330 a full per-judge round-robin would need) it recovers
the true order with tau ≈ 0.76.

## CLI reference

```
brief     <submissions.json> [--out briefs.json] [--model id]
schedule  <submissions.json> --judges <judges.json> --per-judge N
          [--seed N] [--strengths strengths.json] [--out assignments.json]
rank      <results.json>
normalize <scores.json> [--weights '{"technical":2,"design":1}']
simulate  <submissions.json> [--judges N] [--per-judge N] [--seed N] [--noise F]
```

Data shapes: see `examples/` — `submissions.json` (12 infra-hackathon projects),
`judges.json` (5 judges incl. conflict-of-interest exclusions), `results.json`
(pairwise votes `{judge, winner, loser}`), `scores.json` (raw rubric scores
`{judge, project, criterion, score}` with one deliberately harsh and one
deliberately generous judge).

## Environment variables

| Variable            | Required | Effect |
|---------------------|----------|--------|
| `ANTHROPIC_API_KEY` | no       | Enables AI briefs. Without it, briefs use the deterministic heuristic fallback (`"source": "heuristic"`); everything else is pure math and unaffected. |
| `ANTHROPIC_MODEL`   | no       | Override the brief model (default `claude-opus-4-8`). |

Tests never hit the network regardless of environment.
